## AI use

AI chats, autocomplete, and coding agents are permitted throughout the course, including graded work. Students may use them to explain, plan, generate, debug, review, test, document, and revise.

There is:

- no percentage limit on AI-generated code;
- no routine requirement to begin graded work without AI;
- no complete-chat-transcript requirement;
- no automatic penalty for using AI;
- no automatic bonus for avoiding AI;
- no planned reliance on AI-output detectors for grades.

Permission does not transfer responsibility. Before submitting, students should be able to run the work, explain consequential behavior, identify assumptions and plausible failures, show meaningful checks, make an adjacent change, state limitations, and confirm that sharing material with the selected tools was permitted.

> **Recommended loop:** Specify → attempt → ask → inspect → predict → test → revise → explain → disclose

[Read the full AI use and accountability policy](https://github.com/EdenHeilprin/technion-096609-python-ai/blob/main/syllabus/policies/ai-use-and-accountability.md)

## Tool access and equity

Required outcomes will not depend on purchasing an individual AI subscription. The course will publish one free or institutionally funded required route. Paid tools or larger usage limits may be used when available, but should not create a grading advantage unrelated to the learning outcomes.

If a required institutional service fails, the instructor will provide a fallback, additional time, or an equivalent route.

## Short AI work note

When AI substantially affects a submission, this is enough:

```text
Tools:
Purpose:
One consequential contribution:
How I verified it:
```

This is professional disclosure—not an attempt to calculate what percentage was “human-written.”

## Privacy and research data

Synthetic or explicitly approved public data are the default for course exercises, public repositories, demonstrations, and ordinary AI requests.

Never upload:

- passwords, tokens, API keys, or private access links;
- identifiable participant, student, employee, or client data;
- confidential or unpublished research material without explicit authorization;
- private repository content to a service not approved for it;
- licensed/copyrighted material you may not redistribute.

Removing a name does not automatically make a dataset anonymous. Combinations of demographics, dates, text, location, condition, and rare behavior can identify someone.

Use genuinely invented examples such as `SYN001`; do not merely replace the name in a real row.

[Read the full privacy and research-data policy](https://github.com/EdenHeilprin/technion-096609-python-ai/blob/main/syllabus/policies/privacy-and-data.md)

## Public/private GitHub boundary

The public course repository may contain notes, examples, synthetic/public licensed data, starter files, public checks, released material, and documentation.

It must never contain student grades, identity mappings, identifiable/confidential research data, secrets, hidden tests, unreleased solutions, or private student/collaborator content without permission. Student projects are private by default; public release is optional and requires privacy/licensing review.

## Collaboration

Discussion, peer explanation, general strategy, privacy-safe debugging help, and comparison of approaches are encouraged.

On individual work, students may not share a complete current solution/private repository for copying, edit another student's assessed artifact until it becomes their implementation, use an unreleased solution without authorization, or misrepresent who completed an assessed demonstration.

The distinction is accountable ownership—not whether assistance occurred.

Pair-capstone partners are jointly responsible for the whole project's behavior, data contract, reproducibility, and privacy. Repository history supports coordination but is not treated as a simplistic line-count score.

[Read the full collaboration and revision policy](https://github.com/EdenHeilprin/technion-096609-python-ai/blob/main/syllabus/policies/collaboration-and-revision.md)

## Revision

Weekly mastery tasks normally include a correction opportunity before the published cutoff. Effective revision responds to evidence:

1. identify what failed or remained unclear;
2. change the smallest relevant part;
3. rerun the program and checks;
4. state what now supports the result.

Replacing an entire file with a generated alternative may be permitted, but still requires inspection, verification, and explanation.

## Safe technical help

When requesting help, include the operating system, how the file was run, expected behavior, full error text, the smallest relevant code, and what was already tried. Remove identities, secrets, private links, and confidential values. Prefer a structurally equivalent synthetic example when possible.

If protected material is exposed, stop sharing, contact the instructor privately, rotate affected credentials, and remember that deleting a current GitHub file may not erase repository history.
